# Claude Code の /impeccable audit で本番LPを採点してもらった話

検証日: 2026-05-27 〜 2026-05-28
対象: グロースパック for LINE のトップページ（`app/page.tsx`）
ブランチ: `try/impeccable`

## はじめに

最近 Claude Code を触り始めました。
普段はデザイナーで、コードは Claude にお願いして書いてもらう側です。
今回は impeccable という skill（Claude Code に後から追加できる機能パック）を入れて、自分が運用に関わっている本番LPを採点してもらいました。

impeccable は「デザインの品質を測ってくれる skill」と言えばわかりやすいかもしれません。
`/impeccable audit` というコマンドを叩くと、対象ページの実装を読み込んで、accessibility（誰でも使えるか）/ performance（速さ）/ theming（色の整合性）/ responsive（スマホ対応）/ anti-patterns（AI生成あるあるテンプレ）の5観点でスコアを出してくれます。

検証してわかったのは「audit に拾ってもらえる指摘」と「audit には拾えない、人間の目でしか気付けない指摘」がはっきり分かれている、ということでした。
今回はその対比を中心に書きます。

## 結論

| 観点 | わかったこと |
|---|---|
| audit のスコア | features セクション単体で 13/20 → 修正後 18/20（Excellent ライン） |
| audit が拾ってくれること | 数値で測れる問題（コントラスト比、画像サイズ指定、トークン整合性） |
| audit が拾えないこと | ブランド整合、視覚バランス、UI の意図、言葉のおさまり |
| audit の弱点 | 「テンプレに見える」と指摘されたが、LPの慣習として正解な場合もある |
| 役割分担 | audit で機械的に粗削り、人間で意図を入れる、の2段階が現実的 |

## /impeccable audit って何をしてるの

コマンドを実行すると、こういう流れで動きます。

1. プロジェクト直下の `PRODUCT.md` / `DESIGN.md` を読む（プロダクトの文脈情報）
2. 「ブランドLP」「アプリUI」のどっちのページかを判定する
3. 対象ファイルと関連UIコンポーネントを全部読む
4. 5観点でスコアリング、優先度（P0が最重要、P3が軽微）つきで問題を列挙
5. 修正に使う後続コマンド（`/impeccable polish` など）を提案

ポイントは、audit 自体はファイルを書き換えないことです。
スコアと問題リストを出すだけで、修正は別コマンドに委ねます。
人間が「どれを直すか」「どう直すか」を判断する余地が残されている設計だと感じました。

## audit が拾ってくれたこと

具体的に何を指摘してくれたか、代表的なものを並べます。

### 1. コントラスト比の未達（A11y）

「詳細を見る →」のリンクテキストが `#06C755`（LINEグリーン）で、白背景に対してコントラスト比 2.4:1。
WCAG AA の基準（4.5:1）を満たしていないので、低視力ユーザーには読みづらい状態でした。

これは肉眼では「キレイな緑」にしか見えないので、自分では気付けない種類の問題です。
audit が比率の数字で出してくれて、初めて「あ、AA 未達なんだ」とわかりました。

修正方針として、クラスメソッドのコーポレートサイト（classmethod.jp）の本文リンク色 `#2D8DE0`（青）をリンクカラーとして登録して、グロースパックLP内のリンク表現に統一しました。

### 2. 画像の最適化漏れ（Performance）

機能カード内のアイコン画像が、`next/image` の `fill` プロパティで描画されていて、`sizes` 属性が未指定でした。
これだと「1画面ぶんのサイズ」相当の大きい画像が配信されるのですが、実際の表示サイズは 44×44px。
`sizes="44px"` の1行追加で必要十分なサイズだけ配信できるようになりました。

### 3. CSS 変数を使わず HEX べた書き（Theming）

これは前回トップページ全体に audit を当てたときに出た指摘です。
`globals.css` に LINEグリーンの変数 `--color-line-green: #06c755` を定義しているのに、コード側で `text-[#06C755]` と直書きしている箇所が80箇所以上ありました。

「色を変えたくなったら80箇所書き換える羽目になる」状態で、design system として実質崩壊しています。
これも audit に言われるまで気付かなかった種類の問題です。
一括置換で対応しました。

### 4. Identical card grid（Anti-pattern）

これは impeccable が「絶対バン」として明記しているパターンで、

> Same-sized cards with icon + heading + text, repeated endlessly.

機能アセット10個を、同じテンプレートのカードで10枚並べていたのが該当します。
AI が量産したLPによくある形、と判定されました。

ただ、これは「機能一覧」というセクションの目的上、ある程度均一になるのは仕方ない側面もあります。
audit の指摘どおり崩そうとすると、別の何かを失う可能性があるので、今回は対応保留にしました（後述の「注意点」につながります）。

## audit が拾えなかったこと（人間が手作業で直した）

ここからが対比の本題です。
ブラウザで実際に見ながら、自分の目で気になった部分を直していきました。

### ブランドの整合性

- ヒーローの認定バッジ「LINEヤフー Partner Program Technology Partner」を「LINEヤフー Partner Program Technology Partner認定」に修正。文末の「認定」がないと、なんとなく AI が並べただけのキーワードに見える違和感がありました
- バッジ前に置いていた小さな緑色の円のドット装飾を、Award アイコン（賞のアイコン）に変更。AWS Premier の表記で使っているアイコンと統一しました
- スマホ表示時のヘッダー/フッターのアイコンが、v0 のデフォルトアイコン（V字+0のロゴ）のままになっていたので、classmethod 本物のアイコン（V字+階段）に差し替え
- 欧文フォントを classmethod.jp と同じ univia-pro に統一

これらは「ブランドの世界観を揃える」という、ガイドラインを読まないと判断できない領域です。
audit はファイルの中だけを見るので、「このアイコンは v0 のデフォルトのまま」「文末に認定の2文字が足りない」みたいな指摘はできません。

### 視覚バランスの微調整

- ステップバッジ（「顧客接点の創出」など）が、見出しの右下に小さく置かれていたのを、カード左上に移動。フォントサイズを2段階大きく（9px → 14px）
- PRODUCT PREVIEW セクションのバッジで、緑色だけが背景に溶けて見えにくくなっていたので、明度の高い緑（line-green-light）に差し替えてオレンジバッジと視認性を揃えた
- ハーフスクラッチ推奨カードのドロップシャドウを削除。「RECOMMENDED」のリボンと枠線で十分目立っていて、影は過剰でした
- 「AWS Premier Tier Services Partner / ISO 27001」が並ぶ行の上にあった区切り線を削除。線がなくても視覚的に分かれていました

audit のコントラスト判定は「テキスト vs 背景の比率」しか見ないので、「3つ並んでいるバッジのうち1つだけ目立たない」みたいな相対的な見え方の問題は拾えません。

### UI の意図の表現

- ホバー時の浮き上がり表現を、シャドウ（影が落ちる）から border の色変化（緑の枠線が出る）に変更
- クリックした時の青い outline（ブラウザのデフォルトのフォーカス枠）が出るのが気になっていたので、`focus` → `focus-visible` に書き換えてマウスクリックでは出ないように
- リンクのない要素（PROBLEMS カードなど）からホバー浮き上がりを削除。リンクがあるものだけホバーで反応するように整理

「ホバーで何が起きるべきか」「クリックの時に何が出てほしいか」は、デザイナーが普段から判断している領域です。
audit は「outline がある/ない」を機械的にチェックはできますが、「ここは出てほしくない、ここは出てほしい」という意図までは判定できません。

### 言葉のおさまり

- 「こんな課題、ありませんか。」→「こんな課題ありませんか?」に変更。問いかけの文末記号と読点（、）の関係を整える
- フッターの「初回相談は無料です。」を太字+白色で強調
- CONTACT 本文を全幅レイアウトに変更、フォントを2段階大きく、改行位置を調整

文章の語尾や読点の配置は、audit が判定する範囲外です。
ここはコピーライターやデザイナーが自分の語感で決める領域だと感じました。

### セクション構造の組み替え

- 「3ステップで導入できます」を独立セクションから、CONTACT セクションの中へ統合
- FAQ と CONTACT のあいだの余白を縮小

「2つのセクションが意味的に近いから1つにまとめた方が読みやすい」みたいな判断は、ページ全体の構造を俯瞰しないとできません。
audit はセクション単位で見るので、「このセクションは別のセクションに統合すべき」という指摘は出てきません。

## 比較表：audit が見るところ、人間が見るところ

| 観点 | audit が拾える | 人間が見る |
|---|---|---|
| コントラスト比 | ◎（数値で判定） | △（肉眼では限界） |
| 画像最適化 | ◎ | △ |
| トークン整合性 | ◎ | △ |
| anti-pattern マッチング | ◎ | ◯ |
| ブランド整合性 | ✗ | ◎ |
| 視覚バランスの相対比較 | ✗ | ◎ |
| UI の意図表現 | △ | ◎ |
| 言葉のおさまり | ✗ | ◎ |
| セクション構造の俯瞰 | ✗ | ◎ |
| 「LP として機能するか」 | ✗ | ◎ |

audit は「広く・速く・客観的」に問題を出してくれます。
人間は「狭く・遅く・主観的」だけど、ブランドの文脈や使う人の気持ちを考慮できます。

両方が必要、と感じました。
audit だけだとブランドの個性が消えた優等生なLPになるし、人間だけだとコントラスト比のような客観基準が抜け落ちます。

## 注意点：audit の指摘どおりに直さない方がいい場面もあります

検証中に「audit の指摘どおり直したら、逆にLPとして機能しなくなる」ケースが2回ありました。

### 1つ目: STATS セクションの「散文化」を試して戻した

トップページの数字並び（5,000社 / 最短3ヶ月 / 10機能 / 3ステップ）に対して、impeccable は「hero-metric template という SaaS LP の典型パターンに該当する」と指摘してきました。
散文に溶かす形に書き換えてみたのですが、ローカルで見比べた結果、**元の4グリッドの方が LP の意図に合っていた**ため、ロールバックしました。

理由は、B2B のサービスLPでは「数字を並べた信頼設計」がそのまま検討段階の意思決定者に効くからです。
散文化すると数字の物量感が弱まり、速読性が落ちました。

その後、別の落とし所として「4列横並び → 2×2 配置に組み替え」だけ採用しました。
横一列の SaaS テンプレ感は減らしつつ、信頼設計は維持できる構成です。

### 2つ目: Identical card grid を崩さなかった

機能アセット10個のカードグリッドも、impeccable から anti-pattern 指摘を受けました。
ただ「機能一覧を網羅で見せる」というセクションの目的を優先したいので、構造自体は残しました。
そのかわり、コントラストや画像最適化など機械的に直せる部分は全部直しました。

### 共通の学び

audit の anti-pattern 指摘は「テンプレに見える可能性がある」という観点であって、「絶対 NG」ではないようです。
プロダクトの文脈で「これは慣習として正解か、それともテンプレに毒されているか」を判断するのは、最終的に人間の役割になります。

## 修正後のスコア

features セクション単体で再 audit を走らせた結果です。

| # | 観点 | 修正前 | 修正後 |
|---|---|---|---|
| 1 | Accessibility | 2 | 4 |
| 2 | Performance | 3 | 4 |
| 3 | Responsive | 4 | 4 |
| 4 | Theming | 2 | 3 |
| 5 | Anti-Patterns | 2 | 3 |
| 合計 | | **13/20** | **18/20** |

「Identical card grid を構造ごと壊す」未対応の項目を残したまま、最低限の対応で 13→18 まで上がりました。
完璧な 20/20 を狙わず、「人間判断で残すべきもの」を意識的に残せたのが、今回の検証で一番の収穫だったかもしれません。

## まとめ

| 確認したかったこと | 結果 |
|---|---|
| 本番LPを Claude に採点させられるか | できました |
| audit が客観基準で問題を出してくれるか | コントラスト比・画像最適化・トークン整合性は数値で出してくれました |
| audit に拾えない領域があるか | ブランド整合・視覚バランス・UI意図・言葉のおさまりは人間の目が必要でした |
| 指摘どおり直すべきかの判断は | プロダクト文脈で判断、必ずしも全部直すのが正解ではないと感じました |

普段デザイン作業をしているとき、「自分が作ったものを他の人に読み直してもらう」レビューを通すと気付ける問題があります。
今回は「自分が関わったLPを別の Claude（impeccable skill）に読み直してもらう」という構図で、それと近い体験ができました。

Claude Code を触り始めたばかりのデザイナーでも、`/impeccable audit` というコマンド1つで本番ページの健康診断ができるのは、思っていたよりハードルが低かったです。
スコアを上げることだけが目的ではなく、「audit が指摘しないところで何が抜けているか」を考えるきっかけになる、というのが個人的な発見でした。
